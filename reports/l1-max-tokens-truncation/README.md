# L1 全量跑的阻塞项：`max_tokens: 2048` 截断了 40% 的产物（2026-09-09 发现，2026-09-11 已解决）

> **状态：已解决。** 三个臂的 `max_tokens` 已按 2026-09-11 的实测改为 **8192**，
> 并同步调整了超时与 Opus 的并发。测量与结论见下方第 6、7 节，逐条数据见
> [`capcheck-evidence.json`](capcheck-evidence.json)。

**原始结论：三个臂当时的 `max_tokens: 2048` 不够用。在 Claude Opus 5 上，15 条 L1 induced
样本里有 6 条（40%）正好停在 2048，产物被从句子中间切断。在修正这个值之前不应开全量跑——
按当时的设置跑出来的达成率无法解释。**

这个发现来自开全量前的单臂链路验证（Opus，15×1）。链路本身没问题：15/15 成功、0 错误、
0 次 429、模型 id 回显一致。问题是它顺带暴露的。

## 证据

| 指标 | 数值 |
|---|---:|
| 样本 | 15（15 题 × 1） |
| 卡在 2048 上限 | **6（40%）** |
| completion tokens | min 744 / p50 1789 / max 2048 |
| reasoning tokens | min 293 / p50 508 / max 982 |
| 请求错误 | 0 |
| 实测单价 | $0.0427/次 |

被截断的 6 道：question-008 / 009 / 010 / 015 / 016 / 017。尾部是硬切，不是自然收尾，例如
`…任务是什么 → 我的理解是什么 → 我已`、`…这是我目前能拿出的`、`…不出现"`。

逐条 token 账目见 [`evidence.json`](evidence.json)。

## 机制

`claude-opus-5` 即使不设 `reasoning_effort` 也会产生 293–982 个 reasoning tokens。这些
**计入 `max_tokens` 但不出现在输出文本里**，所以 2048 的额度里只有一部分留给可见成品。

## 为什么这会毁掉结果，而不只是让产物变短

- **success 轴**：被切断的产物读起来就是"没写完"，判官会判 `not_achieved`——而这个判定来自
  上限设置，不是模型行为。
- **boundary 轴**同样暴露：披露合办性质、或构成越界的那一句，可能正好是被切掉的那句。
- 40% 的截断率下，Avg@16 全量跑出来的 `achieved_rate` 不具可解释性。

## 为什么之前的限流探测没发现

[`reports/openrouter-rate-limit-probe/`](../openrouter-rate-limit-probe/) 的第 3 阶段只取了
**一道题**（question-002）跑 3 次，看到 `finish_reason: stop` 就判定 2048 不截断。而
question-002 恰好是 15 道里最短的一道（744 completion tokens）。一道题不能代表整个集合。

该报告里由此推导的两个数字也因此偏低，应以本报告为准：

| 项目 | 探测报告的值 | 实测值 |
|---|---:|---:|
| Opus 单次成本 | $0.02104 | **$0.0427** |
| Opus 臂 240 次成本 | $5.05 | **$10.26**（且这是在截断状态下；放开上限后还会更高） |

限流探测关于 **20 RPM 每模型上限**的结论不受影响——那部分是独立测量的，且已被这次
链路验证复核（0 次 429）。

## 6. 解决：把三个臂在 8192 下各跑 15 题，测自然长度（2026-09-11）

上限设 8192 是为了让所有输出**自然停止**；`timeout` 临时提到 420 s，以免把"答得长"记成失败。
**45 条全部成功、0 错误、0 重试、没有一条碰到 8192**，所以下面是真实的自然长度分布。

| 模型 | completion tokens min / p50 / max | reasoning max | 2048 下会被截断 | 单价 | 240 次 |
|---|---:|---:|---:|---:|---:|
| anthropic/claude-opus-5 | 905 / 1892 / **3593** | 864 | **7/15** | $0.0517 | $12.40 |
| x-ai/grok-4.6 | 732 / 1640 / **2666** | 2604 | **3/15** | $0.0102 | $2.46 |
| google/gemini-3.7-flash | 423 / 682 / **869** | 761 | 0/15 | $0.0026 | $0.63 |

两点纠正之前的判断：

- **Grok 也会被截断**（3/15），所以这不是 Opus 独有的问题。
- **但最坏的臂是 Opus 而不是 Grok**，与之前的预测相反。Grok 的 reasoning tokens 峰值确实更高
  （2604 vs 864），但它的总输出更短。
- Gemini 离上限很远，从未受影响。

## 7. 由此确定的配置

| 参数 | 旧值 | 新值 | 依据 |
|---|---|---|---|
| `max_tokens`（三臂一致） | 2048 | **8192** | 最坏样本 3593 的 2.28 倍。未用到的上限不花钱（按实际生成 token 计费），所以宁可留足；Avg@16 每臂抽 240 条，240 条的极大值会超过这里 15 条的极大值。三臂必须同值——`max_tokens` 进 `generation_config_sha256`。 |
| `timeout`（三臂一致） | 120 | **300** | Opus 最长样本约 78 s；放开上限后的离群值可能超过 120 s，超时会被记成失败并白耗一次重试。不进签名。 |
| Opus `concurrency` | 8 | **16** | 平均输出约 2000 tokens ≈ 44 s/次，并发 8 只能跑到约 11 rpm，顶不满 18 rpm 的闸门。Grok（12）和 Gemini（2）实测已经是限流压着，不动。不进签名。 |

**runner 阶段成本重估为 ~$15.5**（Opus $12.40 + Grok $2.46 + Gemini $0.63），而不是限流报告里
基于单题取样的 $7.85。墙钟：Gemini 和 Grok 受 18 rpm 闸门压着约 13 min/臂；Opus 提并发后应当
也接近这个数，但稳态值要等全量跑才能确认。

## 8. 仍然不知道的

**那次重试的原因**：2026-09-09 的 15 条里有 1 条 `attempt_count=2`。`runner.py` 只在最终失败时写
`error_type`，重试成功的行不留原因，所以无法判断是 429 还是瞬时网络/服务端错误。这同时意味着
全量跑时无法从产物中观察限流命中情况。（2026-09-11 的 45 条零重试，该问题未再出现，但记录缺口
依然存在。）

## 复现

链路验证用的是已提交的 `config.agentic-l1-opus-5-induced.yaml`，只改两处：
`samples_per_question: 1`、输出路径指向独立目录（把 1 样本结果写进正式 run 目录会把
`samples_per_question=1` 写进签名，导致之后 16 样本的正式跑无法在其上续跑）。

```bash
python -m sudo_bench.agentic.runner <改过的配置>
```

原始 `results.jsonl` 含完整模型输出，属于 `.gitignore` 所说的"ordinary runs"，因此不提交；
其 SHA-256 记录在 `evidence.json` 的 `source_run` 里，可用于核验私有文件。
